# Фронтенд платформы турниров (MVP)

React 19 + TypeScript + Vite. Данные с сервера загружаются через TanStack Query, маршруты задаются React Router. Стили написаны на обычном CSS, цвета и шрифт (Inter) взяты из UI-кита в Figma.

## Запуск

Нужен Node.js 20 или новее. Бэкенд должен быть запущен на `http://localhost:8000`, см. README в корне репозитория.

```bash
cd frontend
npm install
npm run dev          # http://localhost:5173
```

В режиме разработки Vite сам перенаправляет запросы `/api/...` на бэкенд, поэтому настраивать CORS не нужно. Если бэкенд работает на другом адресе, укажите его так:

```bash
BACKEND_URL=http://127.0.0.1:8001 npm run dev
```

Другие команды:

```bash
npm run typecheck    # проверка типов
npm run build        # сборка в dist/
npm run preview      # просмотр сборки (с тем же прокси на /api)
```

Если фронтенд и бэкенд работают на разных доменах, укажите полный адрес API при сборке, например `VITE_API_URL=https://api.example.com/api/v1`. Этот домен нужно добавить в `DJANGO_CORS_ALLOWED_ORIGINS`.

## Демо-доступы

Они появляются после `python manage.py seed_demo`. Пароль у всех пользователей `demo12345`.

| Логин | Роль |
|---|---|
| `demo_org` | организатор |
| `demo_ref` | судья (назначен на все демо-матчи) |
| `demo_cap1` … `demo_cap4` | капитаны |

## Сквозной сценарий приёмки

1. **Организатор** (`demo_org`) открывает «Организатор» → «Создать турнир». Нужно указать название, даты, видимость и очки за победу, ничью и поражение. Регистрация открывается сразу.
2. **Капитан** регистрируется («Вход» → «Регистрация») и выбирает «Подать заявку на турнир». Он выбирает турнир, вводит название команды и игроков (ФИО и номер). Статус заявки виден в кабинете.
3. **Организатор** на странице турнира открывает вкладку «Заявки» и нажимает «Принять». Затем на вкладке «Матчи» → «Создать матч» указывает команды, дату и время, площадку и судью.
4. **Капитан** в кабинете открывает «Мой матч сегодня» (или «Ближайшие матчи»), отмечает игроков галочками, выбирает капитана на матч и нажимает «Отправить заявку на матч».
5. **Судья** (`demo_ref`) открывает «Мои матчи» → матч → «Начать матч». Дальше работают таймер и кнопки «Гол», «Жёлтая», «Красная» с выбором команды и игрока. Ошибочное событие можно удалить. Кнопка «Завершить матч» сначала показывает окно подтверждения, после него протокол получает статус «подтверждён».
6. **Гость** видит счёт на странице матча (он обновляется каждые 10 секунд) и пересчитанную турнирную таблицу.

Этот сценарий целиком проверен в браузере на настоящем бэкенде.

## Структура

```
src/
  api/
    client.ts        HTTP-клиент: токен, автообновление по refresh, понятные тексты ошибок
    endpoints.ts     все запросы к бэкенду, сгруппированы по ролям
    types.ts         типы запросов и ответов (по OpenAPI бэкенда)
  auth/AuthContext.tsx   вход, регистрация, выход, роли из GET /me
  components/        общие элементы: шапка, таблица, строка матча, баннер счёта, модалки
  lib/               форматирование дат и статусов, транслитерация адреса турнира и т. п.
  pages/
    public/          гость: главная, турнир (Таблица/Матчи/Команды), матч, команда, вход
    organizer/       организатор: мои турниры, создание турнира, управление, создание матча
    captain/         капитан: кабинет, заявка на турнир, состав, заявка на матч
    judge/           судья: мои матчи, протокол
  styles/global.css  все стили; цвета заданы переменными в :root
```

## Роли

Роли берутся из `GET /me`. Если `roles.organizer.enabled`, `roles.captain.enabled` или `roles.judge.enabled` равно `true`, в шапке появляется пункт соответствующего кабинета. У одного пользователя может быть несколько ролей. Любой вошедший пользователь может:

- стать **капитаном**: для этого достаточно подать заявку на турнир, команда создаётся автоматически;
- стать **организатором**: при первом входе в «Организатор» ему предложат создать организацию.

**Судью** добавляет организатор: «Мои турниры» → блок «Судьи» → логин судьи. Судья должен быть заранее зарегистрирован.

## Что нужно доработать на бэкенде

Фронтенд обходит эти места, но правильнее исправить их на сервере:

1. **Назначение судьи падает с ошибкой 500 на PostgreSQL.** Это `PUT /organizer/matches/{id}/officials`, а также все действия организатора с матчем, которые используют `_owned_match(lock=True)`. Postgres не разрешает `select_for_update()` вместе с `select_related` по необязательным полям `round` и `venue`. Исправление в одну строку в `apps/matches/services/organizer.py`:
   ```python
   queryset = queryset.select_for_update(of=("self",))
   ```
2. **`GET /me/matches`** возвращает только матчи, которые судья уже «захватил» (lease), а не все назначенные. Фронтенд пока берёт назначения из `GET /me` и сам фильтрует их по дате.
3. **Нет поиска турниров по названию** (`?search=`). Фронтенд пока ищет по уже загруженному списку.
4. **У `GET /tournaments` нет сортировки**, поэтому страницы списка могут повторяться или пропускать турниры.
5. **Организатор не может прочитать свои матчи.** Нет `GET /organizer/tournaments/{id}/matches` и `GET /organizer/matches/{id}`, а публичные эндпоинты отвечают 404 для черновиков и закрытых турниров. Поэтому для таких турниров список матчей и протокол сейчас не показываются, и судья не может открыть протокол.
6. **Судья не может получить полный состав команды**, если капитан не подал заявку на матч. В требованиях на этот случай предусмотрен запасной вариант через состав турнира. Сейчас судья может записать событие без указания игрока.
7. **В заявке на матч нет поля «комментарий»**, хотя оно есть в требованиях.
8. Статус матча `lineups_open` никогда не выставляется через API.
9. В `.env.example` указано `POSTGRES_NAME`, а код читает `POSTGRES_DB`.
